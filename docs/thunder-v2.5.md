# 雷霆战机 Auto 2.5.0

[一键安装](https://raw.githubusercontent.com/Xiyueyy/sb_auto/main/sb_thunder_auto.user.js)。用法与 2.4 相同：**后台稳定 → 保分仿真**，保分分数设为 **0**。

## 改了什么：回溯修补

原版前瞻规划只往前推演 1～2 秒，偶尔会放跑敌机、补给机，或漏接增益。分析 20 颗种子的原版路线后发现，这类失误是不到 16000 分的主要原因。被击落的情况几乎没有。

2.5 在生成基线路线时逐帧检查失误。目标从屏幕边缘离开就算一次失误，原地消失的击毁或拾取不算，落在屏幕外够不着的道具也不算。发现失误后：

1. 每 32 帧存一次私有引擎快照，只保留最近约 4 秒。
2. 回到 96 或 192 帧前的快照，换一组规划参数重走：决策间隔 5/6/10 帧、推演延长 30/60 帧、漏怪惩罚 ×2～4，共 7 组。
3. 比较事发 96 帧后的局面。只有失误更少，并且分数、生命、火力和连击都不低于原路线时，才替换这一段。
4. 替换前从快照再走一遍，逐帧核对与试走结果一致。

修补后的路线照旧交给 2.4 的整局验分和触控仿真，选中的路线还要在全新引擎实例里回放核对。提交、结算核对和失败即停的逻辑都没有改。

## 时间预算

修补只占用剩余时间。脚本根据已测的规划速度估算剩余基线还要多久，并为整局验分、补交输入和网络预留 75 秒。时间不够就不再修补，剩下的路线按原版生成。修补出错时，会换新引擎按原版重新生成。在本机 Node 上，整局准备约 70～107 秒（3 局并行），服务器时限为 160 秒。

由于修补程度取决于机器速度，同一种子在不同机器上的结果可能略有不同；无论哪种结果，都要通过整局验分才会提交。

有两颗种子下降：6666 降 245，654321 降 10。原因是局部比较窗口只有 96 帧，修补后的路线更晚才会体现代价。仓库原有的 8 颗种子中，平均分从 15629 到 15676，9876543210123456789 从 15820 到 16225，另有两颗各降 15 和 20 分。

每颗种子的数据见 `thunder-script/repair-results.json`。

## 复验

```sh
node thunder-script/test.cjs
node thunder-script/verify.cjs sb_thunder_auto.user.js certified-repair 808 7200 repair
node thunder-script/verify.cjs sb_thunder_auto.user.js replay
```

`certified-repair` 模拟 160 秒时限，走与页面相同的修补、验分和全新实例回放流程。

同 2.4：结果来自离线引擎测试，没有向网站提交新对局，在线结算和反作弊判定都没有验证。
